# Go 模块与插件设计参考

调研日期：2026-09-07。以下事实来自官方文档；“项目建议”是结合 GamePanel Lite 目标作出的设计判断，尚未代表已经实现。

## 1. Go：从使用方需求定义接口

**官方事实：** Go Code Review Comments 建议接口通常由使用方定义，实现方返回具体类型；不要仅为 mock 在实现方创建接口，也不要在出现真实使用需求之前设计接口。文档还要求显式传递 Context、处理错误，并使 goroutine 的退出条件清楚。[Go 官方代码评审建议](https://go.dev/wiki/CodeReviewComments#interfaces)、[Context](https://go.dev/wiki/CodeReviewComments#contexts)、[goroutine 生命周期](https://go.dev/wiki/CodeReviewComments#goroutine-lifetimes)

**项目建议：** 按业务能力分包，用例只依赖自身真正需要的小接口。例如备份用例可以只依赖对象写入能力，无须获得整个存储管理接口。构造函数显式注入依赖，避免全局数据库、全局注册表和服务定位器。

**不直接照搬：** 不要求所有结构体都有同名接口，不建立一个集中收纳全部接口的 `interfaces` 包。共享插件协议可以由宿主契约包持有；使用方小接口与稳定插件协议各有用途。

## 2. Caddy：编译进二进制的可扩展模块

**官方事实：** Caddy 模块提供唯一 ID 和构造函数，按 namespace 对应宿主要求的能力接口；示例用 `init` 注册，`xcaddy` 将插件编译进程序。模块支持可选的初始化、校验和清理接口，并使用编译期接口断言。[Caddy 扩展文档](https://caddyserver.com/docs/extending-caddy)

**项目建议：** 借鉴“稳定标识 + 构造函数 + 能力契约”，先采用编译期插件，在启动装配处显式构造并注册 Provider。每个注册表属于一个应用实例；启动时拒绝重复 ID 和无效配置，启动后不再修改注册表。

**不直接照搬：** 显式注册是本项目建议，并非声称 Caddy 采用此方式。暂不复制其全局 `init` 注册、反射加载、配置热切换及整套通用生命周期框架。现阶段正常编译发布插件即可，不需要热装载。

## 3. HashiCorp go-plugin：有独立发布需求时再引入进程插件

**官方事实：** go-plugin 启动子进程，通过 net/rpc 或 gRPC 通信，支持协议版本及校验和/TLS；插件 panic 与宿主 panic 分离。官方明确它面向本地可靠网络，不支持直接作为真实远程网络插件协议使用。[HashiCorp go-plugin README](https://github.com/hashicorp/go-plugin)

**项目建议：** 未来只有出现第三方独立发布、跨语言或故障隔离需求时，才为特定扩展点增加进程适配器，并规定协议版本、超时、重试语义和资源预算。远程 Agent 应使用单独设计的认证、幂等、重连和状态协议。

**边界推论：** 子进程隔离解决的是内存空间和部分故障传播，不自动限制文件、网络、系统调用或 Docker socket 权限；不能将 go-plugin 当作运行不可信租户代码的安全沙箱。校验和/TLS 也不等于权限隔离。此结论来自其子进程/RPC机制所提供的能力范围，而不是额外的沙箱承诺。[官方架构描述](https://github.com/hashicorp/go-plugin#architecture)

## 4. Go 标准库 plugin：不作为默认方案

**官方事实：** 标准库 `plugin` 动态加载 Go 共享对象，初始化后不能关闭；平台支持有限，race detector 支持不足，对工具链、构建参数和公共依赖一致性有严格要求。官方建议评估静态编译或 IPC 替代方式。[Go plugin 官方警告](https://pkg.go.dev/plugin#hdr-Warnings)

**项目建议：** GamePanel Lite 默认使用静态注册，避免将 `.so` 热加载作为插件化前提。这不妨碍游戏 Provider、RuntimeAdapter、存储或支付适配器在源码层拥有清楚的替换边界。

## 5. 建议落地规则

以下是本项目设计建议，不是上述项目统一规定：

- 业务模块拥有自己的规则与数据写入入口；跨模块调用公开用例，禁止直接写其他模块的表。
- 游戏差异留在 Provider；Docker SDK 留在 RuntimeAdapter；支付和对象存储 SDK 留在各自适配器。
- 业务流程依据接口与能力执行，避免散落的 `switch gameID`、`switch vendor`。
- 不追求消灭全部常量：稳定协议值、状态机及启动装配属于代码；价格、区域、配额与运营策略属于经过校验和版本管理的数据或配置。
- 配置不能授予任意镜像、宿主挂载路径或命令执行权限；扩展能力仍受平台策略约束。
- 用导入依赖检查和适配器契约测试验证边界；新插件应主要增加实现与装配，不要求修改通用运行流程。

推荐顺序：先小接口和显式装配，再固定模块依赖方向及契约测试，最后按实际需求评估进程插件。模块化本身不构成容量或安全保证。
